# Goals and measurements

Stilt aims at six properties at once: Go's compile speed, Rust's safety, C++'s performance, typed and hygienic macros with compile-time code that runs in the editor, Haskell's types and Elm's error handling, read both as no runtime exceptions and as compiler errors that teach ([design sketch](design-sketch.md)). It also aims at a syntax that agents write well ([Agent syntax](agent-syntax.md)), and at costs that the compiler infers and shows rather than ones the programmer proves ([What you write, what is inferred](inferred-facts.md)). This page turns each aim into goals that a script can check, each with its target, how it is measured, and the evidence behind the target.

Every target is set against what incumbent languages achieve on the same measure. Where no incumbent reaches a target, it stays unless it is proven impossible, and the evidence says so.

## How to read the goals

- **Names.** Each goal has a stable name, such as `edit-to-diagnostics`. Budgets, benchmarks and the code that measures a goal refer to it by name.
- **Targets.** A target marked *proposed* is a first estimate, which the first measurement confirms or replaces; it is fixed from then on.
- **After the first release.** A goal marked *after the first release* says where the language is going: nothing builds or measures it yet, and CI doesn't check it.
- **Checked.** CI checks every goal that it can measure on every commit, and a breach fails `just ci`. The goals of agents are measured by studies that run once every tier is built, and the user survey yearly.
- **Timing.** Targets are times on the reference machine, an Apple M4 with 10 cores, 4 for performance and 6 for efficiency, and 24 GB of memory, and also on Linux x86-64. Another program running on the machine changes a measurement's wall time severalfold and its CPU time by half again, so a goal's time is measured by the work's own cycles, all its threads together, taken as time at the reference machine's 4.0 GHz a performance core: the processor counts them for each process, waiting on memory included. Under load the system moves work to the efficiency cores, which take more cycles for the same instructions, so the cycles that count are those the work ran on the performance cores, scaled by all the instructions it retired over those it retired there. Under twice as many busy loops as the machine has cores, a Rust benchmark's wall time grew 3.1 to 3.8 times, its cycles by 3% to 24%, and its instructions and its cycles on the performance cores by nothing ([the meter](../../tools/meter/)). Other programs still change them by what they contend for, the caches and the memory: a release build whose checks touch memory took 1.06 times its wrapping variant's time on an idle machine and 1.11 to 1.20 times under six busy loops. Work spread over several cores counts each core's cycles, so a measurement is the lesser of the cycle time and the wall time: each is at least the time on an idle machine for work that computes rather than waits, so the lesser is the closer bound, and both err on the strict side. Where the system counts no cycles, as on Linux without the kernel's leave, the CPU time stands in for them. A benchmark's time is that of its runs' counts added together, divided by their number, after one warm-up run: one run's share of the performance cores may fall on a phase of the program that is cheaper or dearer than the rest, and the shares of several runs fall on all its phases alike. The goals of the project's own loop, `quick-suite` and `quick-ci`, are the time a developer waits, so they are wall times, judged only where nothing else shares the machine.
- **Workloads.** The generated projects, edit scripts, suites, benchmarks and studies are described under [Workloads](#workloads).
- **Evidence.** Under each table, what incumbents achieve on the same measures, with sources. Incumbents publish typical times, not percentiles, and many don't state their hardware, so their figures rank designs rather than predict Stilt's measurements.
- **Conflicts.** [Goals that seem to conflict](#goals-that-seem-to-conflict) explains how each pair of targets that look incompatible can both hold. [Goals that can't hold as literally stated](#goals-that-cant-hold-as-literally-stated) gives the version of each impossible reading that the goals use instead.

## Priorities

When two goals pull against each other, this order decides. The feature that loses is simplified or moved to a later tier.

1. **One meaning, safely.** Every implementation gives every program the same meaning, and no program has a memory error outside `unsafe`. Nothing is traded for these.
2. **Clarity.** A feature whose common mistakes can't get a clear error stays out (principle 3 of the design sketch). The same goes for syntax that agents can't write reliably.
3. **Speed, by build mode.** Debug builds favour compile speed and release builds favour run-time speed (principle 1). Neither is bought by giving up 1 or 2.
4. **Expressiveness.** Types and macros grow tier by tier, within the budgets above.

## Compile speed (Go)

Rebuilding after a small edit should be close to instant, and clean builds stay acceptable. Release builds spend compile time on run-time speed, so they have no compile-time target; their build times are recorded so the trend stays visible.

| Goal | What it asks | Target | Measured by |
| --- | --- | --- | --- |
| `edit-to-diagnostics` | Edit to diagnostics | Under 25 ms at the 95th percentile on the 50K-line project for body and signature edits through the language server, and under 50 ms replayed on the files, where the database reads every file again to find the one that changed. Under 100 ms for type edits, which check every body that reads the type again | The latency harness replays the edit script against a warm query database and times each edit from the file write to the last diagnostic published ([`just latency`](../../justfile), [tools/latency/](../../tools/latency/)) |
| `edit-to-running-program` | Edit to running program | Under 250 ms at the 95th percentile on the 100K-line project for every edit that patches the program, and under 100 ms for body edits. An edit that changes a type's layout restarts the program | The same harness, timed from the file write until the running program, restarted or not, executes the edited function ([`just latency`](../../justfile), [tools/latency/](../../tools/latency/)) |
| `body-edits-recheck-one-body` | A body edit re-checks only that body | No other body is checked again, even when the edit changes the body's inferred facts, such as its implicit effects ([facts.implicit-effects](../../reference/15-facts.md#facts.implicit-effects)) or the parameters it consumes | Query execution counts in the incremental tests ([`just latency`](../../justfile), [tests.rs](../../compiler/stilt-types/src/tests.rs), [tools/latency/](../../tools/latency/)) |
| `clean-check` | Clean check | Under 1 s on the 100K-line project *(proposed)* | `stilt check` with an empty cache ([`just latency`](../../justfile), [tools/latency/](../../tools/latency/)) |
| `clean-debug-build` | Clean debug build | Under 2 s on the 100K-line project *(proposed)* | `stilt build` with an empty cache ([`just latency`](../../justfile), [tools/latency/](../../tools/latency/)) |
| `compile-time-code-rebuilds` | Compile-time code costs little to rebuild | The compile-time benchmark rebuilds within 20% of its baseline written without compile-time code | Both versions rebuilt after the same edit script ([`just latency`](../../justfile), [bench/compile-time/](../../bench/compile-time/)) |
| `no-slow-edit` | No edit is slow | Every edit of the script under 250 ms on the 50K-line project, whatever depends on it | The latency harness, taking the slowest edit ([`just latency`](../../justfile), [tools/latency/](../../tools/latency/)) |
| `bounded-checking` | Checking time is bounded | Every body of the stress suite checks in under 10 ms *(proposed)* | The stress suite, timed per body ([`just latency`](../../justfile), [tools/latency/](../../tools/latency/)) |
| `one-engine` | One engine | `stilt build` after `stilt check` runs no front-end query again. The language server, the CLI, agents and running programs share one query database, and each meets its own latency target while the others run | Query execution counts; the latency harness with concurrent clients ([`just engine`](../../justfile), [`just latency`](../../justfile), [engine.rs](../../compiler/stilt-cli/tests/engine.rs)) |
| `bounded-cache` | The cache stays bounded | The cache under 500 MB and the engine's footprint under 1 GB for the 100K-line project, and no growth of the cache over repeated replays of the edit script *(proposed)* | The engine's live heap after a clean debug build and after 10 replays, with its process footprint reported beside it ([`just memory`](../../justfile)) |
| `layout-edits-keep-state` | Layout edits keep state | An edit that adds a field with a default, removes a field or appends a variant patches the running program and migrates its live values, within `edit-to-running-program`'s budget *(after the first release: today `stilt run` starts the program again after such an edit)* | The latency harness, on the layout edits of the edit script ([`just latency`](../../justfile), [tools/latency/](../../tools/latency/)) |

The three timings follow the classic response-time limits: 0.1 s feels instant, 1 s keeps the flow of thought, and 10 s holds attention ([NN/g](https://www.nngroup.com/articles/response-times-3-important-limits/)). No incumbent publishes an edit-to-diagnostics percentile. The closest result is Zig's: 63 ms to reanalyse a 500K-line codebase after an edit ([Zig 0.14.0](https://ziglang.org/download/0.14.0/release-notes.html)), and 30–290 ms incremental rebuilds with its own linker ([Zig devlog](https://ziglang.org/devlog/2026/)). Rust's Subsecond patches a running process in 130–900 ms ([HN](https://news.ycombinator.com/item?id=44369642), [dioxus #3797](https://github.com/DioxusLabs/dioxus/pull/3797)). Linking alone takes 1.5–2 s for large debug binaries ([MaskRay](https://maskray.me/blog/2026-04-12-recent-lld-elf-performance-improvements)), and 4 s of a 5 s Go rebuild after a one-file edit ([howardjohn](https://blog.howardjohn.info/posts/go-build-times/)). `edit-to-running-program` therefore rests on the JIT, which never links. In one profiled 37 ms Zig update, analysis took 1.2 ms and about 31 ms went to proving that a dependency graph hadn't changed ([Zig internals](https://news.qurk.cc/2026/07/28/zigs-incremental-compilation-internals/)), the work that durable inputs for the standard library skip (`one-engine`). Erlang makes users write each state migration by hand ([appup cookbook](https://www.erlang.org/docs/28/system/appup_cookbook.md)), and Subsecond doesn't hot-reload structs at all ([docs.rs](https://docs.rs/subsecond)), which `layout-edits-keep-state` goes beyond.

TypeScript 7 checks about 200K lines/s ([Microsoft](https://devblogs.microsoft.com/typescript/typescript-native-port/)), twice `clean-check`'s rate, and Elm builds 850K lines in 5.7 s ([Elm Discourse](https://discourse.elm-lang.org/t/elm-0-19-2-is-live/10841)). Go clean-builds about 100K lines in 4 s, twice `clean-debug-build`'s time, and clang compiles C at about a fifth of its rate, twice as fast as rustc ([HN](https://news.ycombinator.com/item?id=22198188), [nordlow](https://github.com/nordlow/compiler-benchmark)). At `clean-check`'s rate, 25 ms re-checks 2,500 lines, a twentieth of the project. A signature edit with more dependents meets `edit-to-diagnostics` only if re-checking runs faster than a clean check, so `no-slow-edit` bounds every edit. Swift spent 42 s on 12 lines before giving up without a location ([Hooper](https://danielchasehooper.com/posts/why-swift-is-slow/)), which `bounded-checking` rules out.

The cost of missing these targets is measured. About 45% of former Rust users cite compile times as a reason they left. About 60% of current users run `cargo check` after every change, though its work isn't reused by the build, and over 35% call the editor and Cargo blocking each other a big problem ([Rust compiler survey](https://blog.rust-lang.org/2025/09/10/rust-compiler-performance-survey-2025-results)). Disk usage is a big problem for 22.2% ([Rust 2025](https://blog.rust-lang.org/2026/03/02/2025-State-Of-Rust-Survey-results/which-problems-limit-your-productivity.png)).

## Run-time performance (C++)

Release builds target C++ and Rust speed with no tracing garbage collector and no hidden costs. Every ratio below is Stilt's measurement divided by its Rust baseline's, with baselines written under the rules in [Workloads](#workloads).

| Goal | What it asks | Target | Measured by |
| --- | --- | --- | --- |
| `release-speed` | Release speed | Geometric mean of the run-time ratios at most 1, with any one program left out too, and a program that allocates much measured against its baseline linked with mimalloc | The benchmark suite, Stilt in release mode against Rust's release profile ([`just bench`](../../justfile), [budgets](../../bench/budgets.toml), [bench/programs/](../../bench/programs/)) |
| `no-outliers` | No outliers | No run-time ratio above 2 *(proposed)* | The benchmark suite ([`just bench`](../../justfile), [budgets](../../bench/budgets.toml)) |
| `debug-speed` | Debug speed | Geometric mean of the run-time ratios at most 2 for debug builds, and no program's above 6, measured on the same builds as `clean-debug-build` *(proposed)* | The benchmark suite, Stilt in debug mode ([`just bench`](../../justfile), [budgets](../../bench/budgets.toml)) |
| `free-success` | Failure costs nothing on success | The raising variant of the suite runs within 2% of the suite, as a geometric mean, and no microbenchmark slows by more than 10% *(proposed)* | The benchmark suite and its raising variant; the microbenchmarks ([`just bench`](../../justfile), [budgets](../../bench/budgets.toml), [bench/micro/](../../bench/micro/)) |
| `memory` | Memory | Geometric mean of the peak-memory ratios at most 1.2 *(proposed)* | Peak resident memory over the benchmark suite ([`just bench`](../../justfile), [budgets](../../bench/budgets.toml)) |
| `no-hidden-costs` | No hidden costs | Every generic call left on dictionary passing, and the reference-count operations left in each function, appear in the release build's performance report, which `stilt show --release` prints | The report compared with a suite whose costs are known ([tests/costs/](../../tests/costs/), [costs.rs](../../compiler/stilt-cli/tests/costs.rs)) |
| `atomic-counts-where-shared` | Atomic counts only where shared | A reference count is updated atomically only on values that can reach another task, which a bit in the object header records, and `stilt show` prints every such site | A suite whose shared values are known ([`just facts`](../../justfile), [tests/facts/](../../tests/facts/)) |
| `cheap-checks` | Checks cost little | The suite runs within 5% of its wrapping variants as a geometric mean, and no benchmark's checks cost more than 25%, in time or in instructions retired, whichever is less *(proposed)* | The benchmark suite and its wrapping variants ([`just bench`](../../justfile), [budgets](../../bench/budgets.toml)) |
| `small-runtime` | A small runtime | An empty program's peak resident memory is at most 0.25 MB above an empty Rust program's *(proposed)* | The empty programs of the suite ([`just bench`](../../justfile), [bench/empty/](../../bench/empty/), [budgets](../../bench/budgets.toml)) |
| `inline-values` | Values stored inline | In debug builds, no fixed-size record or variant is a heap object, and an `inout` access checks uniqueness at most once *(proposed)* | Counters of allocations and uniqueness checks in debug builds of the benchmark suite ([`just bench`](../../justfile), [budgets](../../bench/budgets.toml), [layout/](../../compiler/stilt-cli/tests/layout/)) |

`debug-speed` holds only if debug builds keep cheap optimizations: values stored inline, with one uniqueness check per `inout` access (`inline-values`); Perceus with borrow inference and reuse; a per-function MIR optimizer that replaces aggregates by scalars, inlines the standard library into user functions and compiles each generic function once per layout shape; checks removed within a function where local analysis proves them; and a standard library compiled once at the backend's highest optimization level. None of them crosses a user function's boundary, so each user function can still be patched on its own (`edit-to-running-program`).

The suite points at what `inline-values` fixes. Binary-trees, which stresses reference counting hardest, runs faster than its Rust baseline, while nbody, the Game of Life and the bytecode interpreter, which update small records, are the slowest. Swiftlet, a compiler for mutable value semantics, ran nbody 4.06 times slower than Swift, and needless uniqueness checks caused most of the loss ([Racordon et al.](https://www.jot.fm/issues/issue_2022_02/article2.pdf)). Lean 4 lost quicksort to MLton and Swift because it boxed array elements ([Ullrich & de Moura](https://arxiv.org/pdf/1908.05647)).

C, C++ and Zig run at 0.8–1.2 times Rust, Nim at 1.34–1.44 and Swift at 1.90–3.61 ([CLBG data](https://salsa.debian.org/benchmarksgame-team/benchmarksgame/-/raw/master/public/data/data.csv), [kostya](https://github.com/kostya/benchmarks)). Swift is the incumbent closest to Stilt's mechanisms: an LLVM optimizer, which Stilt's C output reaches through clang, reference counting, overflow traps and bounds checks. `release-speed` therefore means running 2–4 times faster than Swift, inside the range of C, C++ and Zig. The evidence that this can be done is Perceus. On rbtree, Koka ran between 23% faster and 9% slower than C++, while Swift spends 40–60% of its time in retain and release on the same kind of code ([Perceus TR](https://www.microsoft.com/en-us/research/uploads/prod/2020/11/perceus-tr-v4.pdf), [Ullrich & de Moura](https://arxiv.org/pdf/1908.05647)). Neither paper compares against Rust. The way a suite is written matters as much as the language: Go runs at 2.97 times Rust against the tuned programs of the Benchmarks Game, and at 1.12 on an idiomatic suite. Hence the baseline rules.

Every garbage-collected or reference-counted language exceeds 2 times Rust on some benchmark, and so does clang's C, at 2.47 on k-nucleotide ([CLBG data](https://salsa.debian.org/benchmarksgame-team/benchmarksgame/-/raw/master/public/data/data.csv)). No incumbent of that kind meets `no-outliers`. Most outliers come from the allocation strategy, not from code generation: Rust's binary-trees allocates in an arena and takes 1.07 s, while Swift's allocates each node through reference counting and takes 17.6 s ([Rust](https://benchmarksgame-team.pages.debian.net/benchmarksgame/program/binarytrees-rust-5.html), [Swift](https://benchmarksgame-team.pages.debian.net/benchmarksgame/program/binarytrees-swift-4.html)). The baseline rules keep the comparison fair until Stilt has arenas.

Rust's own debug builds commonly run 10–100 times slower than its release builds ([Rust Performance Book](https://nnethercote.github.io/perf-book/build-configuration.html)), so `debug-speed` is stricter than Rust and needs the optimizations above. Swift returns errors in a register, which costs one predicted branch per call ([Mike Ash](https://www.mikeash.com/pyblog/friday-qa-2017-08-25-swift-error-handling-implementation.html)). The same design cost about 10% on fib, which does almost nothing but call, and nothing measurable on code that computes ([P2544R0](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2022/p2544r0.html)). `free-success` therefore takes a mean over the suite and caps microbenchmarks separately.

On memory, Go reaches 1.06–1.62 times Rust, Nim 1.35 and Swift 2.96–3.74 ([CLBG data](https://salsa.debian.org/benchmarksgame-team/benchmarksgame/-/raw/master/public/data/data.csv), [PLB](https://programming-language-benchmarks.vercel.app/rust-vs-swift)). Several Rust benchmarks peak at 3–4 MB, so `memory` needs `small-runtime`'s small runtime. Atomic counts everywhere cost Koka 5–59% and Lean 1.52 times. Overflow checks cost rustc's tests 0.6–2.7% ([#87784](https://github.com/rust-lang/rust/pull/87784)), but a check that blocks vectorization slowed a summing loop 3–12 times ([Lemire](https://lemire.me/blog/2020/09/23/how-expensive-is-integer-overflow-trapping-in-c/)), which `cheap-checks` watches. Unpredictable costs drive users away: only 23.4% of Haskell users can easily reason about their code's performance ([State of Haskell 2025](https://discourse.haskell.org/t/state-of-haskell-2025-results/13755)), and Apple calls the variability of Swift's reference counting difficult for performance work ([Swift forums](https://forums.swift.org/t/a-roadmap-for-improving-swift-performance-predictability-arc-improvements-and-ownership-control/54206)).

## Safety (Rust)

| Goal | What it asks | Target | Measured by |
| --- | --- | --- | --- |
| `no-memory-errors` | No memory errors outside `unsafe` | No sanitizer finding | AddressSanitizer and LeakSanitizer on the runtime, over every conformance run test and the nightly generated programs, on Linux ([`just sanitizers`](../../justfile), [tools/linux/](../../tools/linux/)) |
| `no-leaks` | No leaks | Every reference count is back to zero at exit | The check debug builds make at exit, on every run test and generated program ([`just run`](../../justfile), [counting.rs](../../compiler/stilt-cli/tests/counting.rs)) |
| `sound-typing` | Sound typing | The core typing and mode rules are stated in Lean and compile, and the Lean model has no open soundness issue | `formal/` builds with no `sorry`, no axiom of its own, and a soundness theorem that rests on Lean's three standard axioms alone ([`just formal`](../../justfile), [formal/](../../formal/)). The theorem covers a core calculus: of the Reference's 1000 paragraphs, 247 fall under it, 27 more are modeled in calculi of their own, 20 are described, and 706 aren't modeled, as [the proof map](../../tools/proof-map/) counts them |
| `exclusivity` | Exclusivity | Every program that the rules of [Modes and exclusivity](../../reference/13-modes.md) reject is rejected, by the reference interpreter and the compiler alike | Conformance and differential checking ([`just conformance`](../../justfile), [`just differential`](../../justfile), [conformance/modes/](../../conformance/modes/)) |
| `visible-unsafe` | `unsafe` is visible | Every `unsafe` block carries a written justification, and `stilt show` lists the blocks, each on its line with its justification. `unsafe` blocks and foreign calls are inferred facts, shown next to each signature: `without unsafe` keeps them out of a module or a function, and a package's manifest keeps them out of its dependencies. In the compiler's own code, only the runtime and the Cranelift backend use `unsafe`, and the standard library uses none outside the runtime | `just lint`, which prints the count of `unsafe` blocks; conformance ([`just lint`](../../justfile), [`just conformance`](../../justfile)) |

Rust's guarantee is the most measured. Android's Rust code has about a thousandth of the memory-safety vulnerability density of its C and C++, with a quarter of the rollback rate ([Google](https://blog.google/security/rust-in-android-move-fast-fix-things/)). 77.8% of C++ developers call memory safety important or essential ([ISO C++ 2025](https://isocpp.org/files/papers/CppDevSurvey-2025-summary.pdf)), and use-after-free bugs drove Bun from Zig to Rust ([Willison](https://simonwillison.net/2026/Jul/8/rewriting-bun-in-rust/)). Stilt's `core` reaches the guarantee through value semantics ([The value model](../../reference/05-values.md)), and its later tiers through inferred modes, rather than through a borrow checker, so these requirements test the outcome, not the mechanism.

## Failure in types (Elm)

| Goal | What it asks | Target | Measured by |
| --- | --- | --- | --- |
| `failure-in-types` | Every way a function can fail or touch the world is in its type | Every paragraph of [Effects and handlers](../../reference/12-effects.md) has an accepted and a rejected test | The coverage report ([`just coverage`](../../justfile), [conformance/effects/](../../conformance/effects/)) |
| `without-panic` | `without panic` rules out every panic but overflow, which `without overflow` rules out, and `deadlock`, which a `when` reached through a function value may meet | Each panic kind but overflow is rejected under `without panic`, and each operation that can overflow under `without overflow`, on a module and on a function | Conformance ([`just conformance`](../../justfile), [conformance/effects/](../../conformance/effects/)) |
| `one-panic-report` | Panics are reported the same way everywhere | Exit status 101 and the report of [program.panic-report](../../reference/04-programs.md#program.panic-report), identical under the reference interpreter and every build | Differential testing ([`just differential`](../../justfile), [conformance/program/](../../conformance/program/)) |
| `contained-failures` | New failures don't spread | Adding a variant to an error type breaks only the exhaustive matches and catches on that type. Callers that pass the error on, or that are generic over the row, compile unchanged | Conformance ([`just conformance`](../../justfile), [conformance/effects/](../../conformance/effects/)) |
| `no-escaping-effects` | No effect escapes | Performing a user-defined effect outside every handler for it, and resuming a one-shot continuation twice, are compile errors | Conformance ([`just conformance`](../../justfile), [conformance/effects/](../../conformance/effects/)) |

Elm reports no runtime exception from more than 80,000 lines of production code since 2015, a self-reported record ([QCon 2017](https://archive.qconlondon.com/london2017/presentation/full-scale-elm-production)). Go shows what is lost without typed failure. Error-handling verbosity is one of its users' oldest complaints, their write-in wishes ask for enums, sum types and nil safety, and in 2025 the Go team stopped trying to fix error handling with syntax ([Go blog](https://go.dev/blog/error-syntax), [Go survey 2025](https://go.dev/blog/survey2025)). Checked exceptions show the opposite risk: Java developers mostly log or swallow them ([MSR 2016](https://www.computer.org/csdl/proceedings-article/msr/2016/07832935/12OmNxwENxJ)), because adding one breaks every client ([Hejlsberg](https://www.artima.com/articles/the-trouble-with-checked-exceptions)). `contained-failures` holds through rows generic in their error, function arguments whose effects pass through to the caller, `try` that costs one token, and catch-alls that must give a reason when they drop the error ([Effects and handlers](../../reference/12-effects.md)). OCaml 5 reports an unhandled effect only at run time ([OCaml manual](https://ocaml.org/manual/5.3/effects.html)), which `no-escaping-effects` rules out.

| `foreign-syntax-named` | Syntax from other languages is named | Every program of the foreign-syntax suite gets exactly one diagnostic, which names the Stilt form | The foreign-syntax suite ([tests/diagnostics/](../../tests/diagnostics/)) |
| `mismatch-diffs` | Mismatches show a diff | A mismatch between two record, function or generic types shows only the parts that differ, as the user wrote them | Snapshot tests ([`just diagnostics`](../../justfile), [tests/diagnostics/](../../tests/diagnostics/)) |
| `compile-time-errors-at-user-code` | Errors in compile-time code point at the user's code | Every diagnostic raised by or in an expansion or a compile-time call points at tokens the user wrote, and names the macro or the chain of compile-time calls | Snapshot tests on the compile-time benchmark ([`just diagnostics`](../../justfile), [bench/compile-time/](../../bench/compile-time/)) |
| `admissible-alternatives` | Diagnostics list admissible alternatives | Wherever the checker can enumerate them, a diagnostic's JSON lists the admissible alternatives: bindings of the expected type, missing variants, effects the row allows, methods with a close name, at most 10 *(proposed)* | A schema check over the JSON snapshots, and a suite whose alternatives are known ([`just alternatives`](../../justfile), [tests/alternatives/](../../tests/alternatives/), [alternatives.rs](../../compiler/stilt-cli/tests/alternatives.rs)) |
| `total-recovery` | Recovery is total | Every program with up to five planted mistakes, each in a different body, gets exactly one diagnostic per mistake, on its line, as the Reference's recovery rules define *(proposed)* | The mutation suite in its multi-mistake form, checked by the reference interpreter and the compiler ([`just mutated`](../../justfile), [tools/generator/](../../tools/generator/)) |

Rust sets the bar: only 7.38% of its users call unclear error messages a big problem ([Rust 2025](https://blog.rust-lang.org/2026/03/02/2025-State-Of-Rust-Survey-results/which-problems-limit-your-productivity.png)). C++ developers ask for Rust-style diagnostics ([ISO C++ 2025](https://isocpp.org/files/papers/CppDevSurvey-2025-summary.pdf)), and error messages were Clojure's top frustration for years ([State of Clojure 2016](https://clojure.org/news/2017/01/31/state-of-clojure-2016)). Elm shows the code as written, with a hint ([Elm](https://elm-lang.org/news/compiler-errors-for-humans)), and only the parts of two types that differ ([Elm](https://elm-lang.org/news/compilers-as-assistants)). Research on enhanced messages is mixed: a replication found the same error repeated 13.71% of the time after standard messages and 13.99% after enhanced ones ([Pettit et al.](https://files01.core.ac.uk/download/pdf/212852141.pdf)). `quick-fixes` therefore measures fixes instead of assuming them.

Agents need more than people do. The full chain of constraints raised one model's repair rate from 47.8% to 63.4% when it came with locations ([Krishnamurthi & Flatt](https://arxiv.org/html/2606.01522v2)). Feedback that lists admissible alternatives raised one agent loop's success from 28% to 72%, and almost all of the gain came from the alternatives, with prose doing as well as JSON ([Ray & Goyal](https://arxiv.org/abs/2607.14167)). Hazel's marked lambda calculus gives every program a type and continues checking around each error ([Zhao et al.](https://hazel.org/papers/marking-popl24.pdf)), while Roc's recovery, added after its checker was built, still let rejected code reach lowering in September 2026 ([roc #11858](https://github.com/roc-lang/roc/pull/11858)). `total-recovery` asks for the first. Syntax borrowed from other languages caused 83.9% of zero-shot failures in a new language ([CangjieBench](https://arxiv.org/html/2603.14501)). Macro errors that point only at the call site are a known Lisp pain ([jank](https://jank-lang.org/blog/2025-03-28-error-reporting/)), and Racket's syntax-parse shows the alternative ([Culpepper & Felleisen](https://www2.ccs.neu.edu/racket/pubs/icfp10-cf.pdf)).

In the one rigorous measurement of tokens per solved task, Python was the cheapest language for every model tested. Java cost 1.18–1.34 times its output tokens, Rust 1.16–1.57 and OCaml 1.28–1.69, at nearly equal accuracy ([Wu et al.](https://arxiv.org/html/2607.22807v1)). `tokens-per-task` asks for a first, from a language models were never trained on. The extra tokens go to the error loop, not to longer programs: the final source is only 4.5–8.4% of output tokens, so a shorter syntax saves little.

The levers are the error loop (`one-form-per-reader`, `foreign-syntax-named`, `admissible-alternatives`, `repeated-failures-flagged`), a guide in context (`guide-fits-context`), a suite (`training-corpus`), holes that report their context (`hole-context`), properties (`property-counterexamples`) and constrained decoding (`prefix-decidable-checking`, `published-grammar`). A 2,146-token syntax reference lifted a new language's pass rate from 2–15% to 24.6–50.4% ([CangjieBench](https://arxiv.org/html/2603.14501)). Translations validated by tests brought Lua and Julia to Python's level on a 15B model ([MultiPL-T](https://arxiv.org/html/2308.09895v5)). Type-constrained decoding cut compile errors by 75.3% on HumanEval and 52.1% on MBPP, where a perfect syntax-only constraint would have removed 9.0% and 4.8% ([Mündler et al.](https://arxiv.org/abs/2504.09246)). Function headers tripled GPT-4's test performance in Hazel's study once types were present ([Blinn et al.](https://arxiv.org/html/2409.00921v1)), and property feedback raised pass@1 by 23–37% relative to test-driven baselines ([PGS](https://arxiv.org/html/2506.18315v1)).

On success, frontier agents with a test loop score about the same in Python, Java, Rust and OCaml on self-contained problems. A GPT-5 agent reached 84.8% on HumanEval in Cangjie, a language with almost no training data. Strict types help agents when ill-typed code can't run. Rust leads SWE-bench Multilingual at 58.1% against Go's 31.0% ([SWE-bench Multilingual](https://www.swebench.com/multilingual.html)). TypeScript that runs despite failing its checks "can gaslight the agent" ([Ronacher](https://lucumr.pocoo.org/2026/2/9/a-language-for-agents/)), whereas a Stilt program with errors stops with `check-error` where it reaches one, and its run always exits with status 2 (`programs-with-errors-run-alike`).

## Goals that seem to conflict

Several targets look as if they must trade off. Each pair below conflicts only under one implementation, and the goals choose another, so none is dropped.

| Goals | How both hold |
| --- | --- |
| Short messages (`short-messages`) and the detail agents need (`one-form-per-reader`, `admissible-alternatives`) | Each reader gets its own form: people get the short message, and `check --json` adds the chain of constraints and the admissible alternatives |
| Haskell's types and a 25 ms edit loop (`local-inference`, `edit-to-diagnostics`) | Inference stays inside bodies and nothing is overloaded, so an edit re-checks only its dependents and no expression searches (`bounded-checking`) |
| Inferred costs and local checking (`shown-facts`, `body-edits-recheck-one-body`) | Facts are inferred from bodies but kept apart from the signatures that type checking reads, so a body edit re-checks no caller, and `show` prints the facts for readers without an editor |
| Lisp's macros and Go's compile speed (`compile-time-code-rebuilds`, `visible-expansion-size`) | Compile-time code runs in an interpreter inside the compiler, is cached by a hash of its input and of what it read, and its output size is measured |
| Rust's safety and C++'s speed (`release-speed`, `cheap-checks`) | Checks cost little outside vectorized loops, and release builds drop the checks that verification proves |
| Fast debug runs and fast debug builds (`debug-speed`, `clean-debug-build`) | Debug builds keep only cheap optimizations and an optimized standard library, and both targets are measured on the same builds |
| Debug optimizations and hot patching (`debug-speed`, `edit-to-running-program`) | No debug optimization crosses a user function's boundary, so each function can still be patched alone |
| Inline values and live edits (`inline-values`, `edit-to-running-program`) | A layout edit restarts the program, or migrates its live values (`layout-edits-keep-state`); every other edit patches one function |
| No tracing garbage collector and Rust-class memory (`memory`) | Perceus frees memory at the last reference and reuses it in place, so there is no garbage to hold: Koka used 135 MB on rbtree where C++ used 200 MB ([Koka](https://github.com/koka-lang/koka/blob/master/test/bench/readme-icfp22.txt.md)) |
| Typed failure and APIs that evolve (`failure-in-types`, `contained-failures`) | Rows generic in their error leave intermediate callers unchanged, a function argument's effects pass through to the caller, `try` costs one token, and catch-alls that drop the error must give a reason |
| No cost on success and cheap raises (`free-success`) | An error returned in a register costs a predicted branch per call, and a raise stays an ordinary return, so neither needs table-based unwinding |
| Stability and fixing mistakes (`additive-features`, `migrations`) | Deferred features are additive, and every break ships its rewrite |
| Strict types and agent success (`agent-success-rate`, `programs-with-errors-run-alike`) | A program with errors stops with `check-error` at the first code with an error that it reaches, and its run always exits with status 2, so no harness mistakes it for success; and errors name their fix |
| No runtime exceptions and reach through FFI (`failure-in-types`, `visible-unsafe`) | FFI is typed, listed `unsafe` in the `systems` tier, rather than forbidden as Elm forbids native modules |
| Compiled code and Lisp's interactivity (`interactive-evaluation`, `edit-to-running-program`) | A REPL and live edits on the debug backend |
| C output and one meaning (`release-runs-like-debug`) | The emitted C never reaches C's undefined behaviour: overflow goes through checked builtins, wrapping arithmetic through unsigned types, a shift checks its amount and a division its divisor, and three-way differential testing checks the result |
| Parallel speed and one meaning (`parallel-like-sequential`) | Only closures with an empty row run in parallel, so the parallel result is the sequential one, which the reference interpreter computes |
| Python's token cost without Python's training data (`tokens-per-task`) | The guide in context, the error loop with its alternatives, holes that report their context, a validated suite and constrained decoding stand in for training data |

## Goals that can't hold as literally stated

Five readings of the goals are impossible, either by a proven result or by construction. Each has a version that holds, and the goals use that version.

- **No run-time failure of any kind.** Whether an arbitrary program overflows, runs out of memory or terminates is undecidable (Rice's theorem). A compiler can rule out every panic only by rejecting correct programs or by changing what operations mean. The Reference draws the line instead. `without panic` rules out every panic but overflow and `deadlock` ([effects.without-panic](../../reference/12-effects.md#effects.without-panic)). Possible non-termination is the inferred fact `div`, and `without div` accepts only recursion and loops that the compiler can see end, by a part of a parameter, or by a counter that steps toward its bound or an argument that shrinks toward one ([Inferred facts and limits](../../reference/15-facts.md)), so it rejects some programs that do terminate. Stack overflow and running out of memory abort with status 134 ([program.exit-statuses](../../reference/04-programs.md#program.exit-statuses)). Every other failure is in a function's type (`failure-in-types`, `without-panic`).
- **Every mistake reported where it was made.** Two correct programs, each changed at a different line, can produce the same text, so no checker can always name the changed line. In `let n: i64 = "3"`, either the annotation or the literal may be the mistake. `root-causes` and `quick-fixes` hold because the mutation suite contains only mistakes that the Reference pins to one line.
- **Patching any edit into a running program.** A value built with a type's old layout has no defined value under a new one in general: a field whose type changes has nothing to convert from. Adding a field with a default, removing a field and appending a variant each have one obvious migration, which the live edit loop applies (`layout-edits-keep-state`). Every other layout edit restarts the program (`edit-to-running-program`).
- **Python's token count with the guide counted.** Python solves typical tasks in 600–900 output tokens ([Wu et al.](https://arxiv.org/html/2607.22807v1)), fewer than a useful guide holds. Counting the guide as output would leave fewer than zero tokens for the task, so `tokens-per-task` counts output tokens and reports the guide as input.
- **Haskell's types with no signatures.** Inferring higher-rank types without annotations is undecidable (Wells, 1999). Signatures are required at item boundaries (`local-inference`), and higher-rank types arrive in the `advanced` tier with annotations.

## Workloads

- **Scale projects.** `tools/generator` in scale mode generates `core` projects of 50K and 100K lines from fixed seeds. The generator's version is pinned with the budgets, so measurements compare like with like.
  - **Pinned.** `just scale` writes both. The 50K-line project comes from seed 1 and has 50,769 lines in 238 files; the 100K-line project comes from seed 2 and has 100,539 lines in 495 files. A change to the generator that changes these sizes changes the workload, and the budgets measured on it are measured again.
- **Edit scripts.** One-line edits from a fixed seed, each followed by its undoing, of six kinds in turn: a statement added to a body, one that can panic, one with a type error, a parameter added to a function, a variant added to the type of the module the most modules import, and a function added to a module. The function and file of each are picked uniformly, and the bodies each checks again are recorded with its time. The replays that time edit-to-diagnostics, against the database and through the language server, make 100 edits of each kind, so each kind's 95th percentile is drawn from 100 edits and that of body edits from 300; the replay that compares each step with a clean check, and the one against a running program, make 8 of each, since each of their steps costs a clean check or a build. The harness prints beside each percentile how many edits it is drawn from.
- **Stress suite.** Bodies built to stress inference, generated by `tools/generator` from fixed seeds: deep nesting, long method chains, large `match` and `if` trees, and literals whose type is known only late.
  - **Pinned.** `just stress` writes the suite: 200 programs from seeds 1 to 200, 50 of each kind. Each holds one function whose body is 100 to 250 levels deep, a chain of 50 to 200 calls, a `match` or `if` tree of 100 to 400 branches, or 100 to 300 statements whose literals take their type from the body's last statements.
- **Mutation suite.** `tools/generator` in mutation mode plants one mistake in a correct program. Each mutation is chosen so that the Reference requires exactly one diagnostic for it, at the mutated line, so the expected result is known without running any implementation. In its multi-mistake form, it plants up to five mistakes, each in a different body (`total-recovery`).
- **Facts suite.** Programs whose inferred facts are known by construction: the parameters each function consumes, where it allocates or panics, its tier, its modes and its capabilities. `shown-facts` and `no-hidden-costs` compare the tools' output with it.
- **Compile-time benchmark.** A program heavy in compile-time code, with reflective derives, procedural macros and compile-time parameters, and a baseline that writes the same code by hand (`compile-time-code-rebuilds`, `editors-see-expansions`, `visible-expansion-size`, `compile-time-errors-at-user-code`).
- **Foreign-syntax suite.** One program per construct that Rust, TypeScript, Python or Swift write differently from Stilt, starting with the most frequent mistakes in the transcripts of the agents that build Stilt, then in those of the agent study.
- **Benchmark suite.** About 15 programs, each with a Rust baseline that prints identical output. Among them are binary-trees, n-body, spectral-norm, fannkuch, JSON parsing, a map-heavy program and a string-heavy program.
  - **Baseline rules.** Each baseline is idiomatic safe Rust with the same algorithm, the same threading and a library of the same class. It uses `unsafe`, SIMD intrinsics or arenas only where the Stilt program uses the equivalent feature.
  - **Variants.** In each program's raising variant, every function's row raises and every call goes through `try`, though nothing raises (`free-success`). Its wrapping variant uses wrapping operators and, where the algorithm allows, iteration instead of indexing (`cheap-checks`).
  - **Baselines.** An empty program in each language measures the runtime's fixed memory (`small-runtime`). Microbenchmarks, such as `free-success`'s, live beside the suite.
- **Tokenizer basket.** Token counts use public tokenizers, starting with `o200k_base` and `cl100k_base`, and are measured again each year.
- **Agent study.** 100 small, self-contained tasks ported to Stilt, Python, Rust and TypeScript, each run 5 times per language with current frontier models. Agents get the agent guide and the verdict of `test --json`. The study records task success, output tokens per solved task with the guide reported as input, and how often agents turn to Python as a scratchpad. Ratios are estimated with a per-task random effect, as Wu et al. did. Three features are also turned off in turn, as ablations, so each claim stays falsifiable: constrained decoding (`prefix-decidable-checking`, `published-grammar`), the context of holes with the alternatives of diagnostics (`hole-context`, `admissible-alternatives`), and properties (`property-counterexamples`); each ablation records tokens per solved task, compile loops and refused edits. It runs once every tier has been built, as do the error-tax study on the mutation suite and the macro study.
- **User survey.** Yearly once Stilt is released, with the incumbents' wording.

## Enforcement

- **Budgets.** `bench/budgets.toml` holds one entry per measured goal, keyed by its name. `just ci` fails when a measurement exceeds its budget.
- **Claims.** Each goal's *Measured by* links to the tests, suites, recipes or budgets that check it, or says that a study, a survey or a review by people measures it, and `just site` fails on a goal that does neither, so no claim on the site stands without something that can falsify it.
- **No waivers.** A goal that can't be met isn't waived. The design gets simpler until it holds, and the Reference's rationale says what changed.
