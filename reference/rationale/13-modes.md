# Rationale: Modes and exclusivity

Stilt has value semantics, no tracing garbage collector and no references that a program can store, and it promises no hidden costs. Two parameter modes, `let` and `inout`, and one law about overlapping accesses make those fit together. They let `inout` mean copy-in, copy-out while a compiler changes places in memory directly. On top of them, the compiler infers facts about how each value is used. The advanced tier adds views and projections, which look into and write through values that someone else owns, without lifetimes.

## Places and accesses

The law of exclusivity is stated over places and accesses, and both are syntactic ([modes.places](../13-modes.md#modes.places), [modes.overlap](../13-modes.md#modes.overlap), [modes.kinds-of-access](../13-modes.md#modes.kinds-of-access)). Overlap removes indexes before it compares places, so `xs[i]` and `xs[j]` overlap whatever `i` and `j` are. The check never looks at values. The reference interpreter implements it as a syntactic pass over each body, and the compiler on its mid-level representation, with identical results.

Durations are lexical ([modes.durations](../13-modes.md#modes.durations)): an access lasts for a span of the source text, and not until its last use. Flow-sensitive durations, as Rust's non-lexical lifetimes give, would accept more programs. They are rejected. No tier has references that can escape, so little is lost. The extra precision isn't worth a rule that is harder to state, and that two implementations could read differently. The advanced tier's views keep the same lexical durations.

A `let` argument is a read that ends before the call starts. A read that lasts for the whole call is rejected: it would reject common, harmless code such as `xs.push(xs[0])`, and the value model already makes each argument an independent copy. An implementation still passes a `let` argument by reference, and copies it only when the same call modifies an overlapping place.

## The law of exclusivity

The law ([modes.law](../13-modes.md#modes.law)) is what makes copy-in, copy-out and changing a place in memory agree. With two overlapping `inout` arguments ([modes.overlapping-inout](../13-modes.md#modes.overlapping-inout)), the result would depend on the order in which they are written back, so the call is rejected. With the law, the reference interpreter's model of `inout` can't be told apart from mutation in place. Swift's `inout` and its own law of exclusivity follow the same idea, and Hylo builds its design on parameter modes much like these. No mode can be stored or returned, so an `inout` parameter can't outlive its call, and no tier needs lifetime annotations.

Changing a list while a loop reads it is an error ([modes.change-while-iterating](../13-modes.md#modes.change-while-iterating)). Under copy-on-write such a change can't corrupt memory. It would silently copy the whole list, and the loop would go on reading the old contents: a hidden O(n) cost, and behaviour that surprises the reader. The alternative is to allow the change with snapshot semantics, which is memory-safe but hides the copy. Any other write to shared data copies it without a diagnostic, and only this case is both silent and surprising. The error offers the two rewrites that keep the intent, `retain` and collecting the changes for after the loop.

Closures capture by copy and can't modify what they capture ([modes.closures](../13-modes.md#modes.closures)), so in core they take no part in the law. A closure that must change the caller's place takes it as an `inout` parameter. Only `var` bindings and `inout` parameters can be modified ([modes.what-can-be-modified](../13-modes.md#modes.what-can-be-modified)). A modification of what can't be modified is reported alone, since the fix, rebinding with `var x = x`, also changes which accesses conflict.

## Modes

Whether a callee consumes an argument, and may reuse its memory, is a fact that the compiler infers, and is no mode. The advanced tier adds features whose costs and safety depend on more such facts. These features are views that can't escape the function they come from, closures that may run in parallel, values sent to another task, and shared values that several tasks reach. Rust answers each with something the programmer writes: lifetimes, `Send` and `Sync`, `FnOnce`. Stilt infers them, as five modes of every binding ([modes.bindings-and-axes](../13-modes.md#modes.bindings-and-axes)), and the tools show them.

There are five axes. Folding once into uniqueness, and contention into portability, would shorten every message. `par` then couldn't tell a closure that reaches a `Shared<T>`, which is safe to send and unsafe to run in parallel, from one that holds a view, which is neither. A handler's one-shot continuation would also have no axis to live on.

A mode is a fact, never part of a type ([modes.fact-not-type](../13-modes.md#modes.fact-not-type)). Making modes part of a function's type, as `inout` is, is rejected. A binding's mode would reach its callers' types, so editing a body could check every caller again. Every signature would also carry modes that change whenever a body starts reusing memory. Written modes, as OCaml's `local_` and `once_` or Hylo's `sink`, are rejected for the reason that rejects a written `own`. They declare a compilation strategy that no observation can tell apart, and the compiler infers the same information. Facts cost nothing to carry, and a package's API doesn't hold them.

A mode changes nothing a program means. The Lean model states this as a theorem. Evaluation with every mode at its default agrees with evaluation that reuses a `once` closure's captures and the memory of `local`, `unique` values. So the reference interpreter infers no mode, and the facts suite checks modes in place of the conformance suite.

## Locality

A binding escapes where its value leaves the function ([modes.escaping](../13-modes.md#modes.escaping), [modes.not-escaping](../13-modes.md#modes.not-escaping)). Only values of copy-on-write types can be shared, so only they have a locality worth recording. Passing `inout` and capturing in a closure that stays in the function don't make a value leave: it comes back, or dies with the function. The compiler reads locality where it reads consumption, to keep a value in place and to reuse its memory.

## Uniqueness

A write may copy when another path to the value may still exist ([modes.copies](../13-modes.md#modes.copies), [modes.shared-writes](../13-modes.md#modes.shared-writes)). A copy passed to a consumed parameter lasts as the call's result does, because the callee may keep the copy in its result. The rule is lexical and conservative: a copy held by a binding counts until the binding's scope ends, whether or not the binding is used again. Flow-sensitive uniqueness, which would make `var xs = ys; drop(ys); xs.push(1)` unique at the push, is rejected for the reason that keeps durations lexical. The compiler may still reuse memory where it knows more, since the fact is a conservative bound, as `alloc` is. The `copy` effect and `without copy` read the shared writes, so a reader can rule out the copies that copy-on-write makes.

## Once

A closure that runs at most once may give its captures up at its call instead of copying them ([modes.once-closures](../13-modes.md#modes.once-closures), [modes.once-parameters](../13-modes.md#modes.once-parameters)), as a consumed parameter may reuse its argument. A closure literal passed to a `once` parameter inside a loop is `once` too, since each turn of the loop makes a new closure. The rules are syntactic, and recursive groups are solved as a fixed point, as implicit effects are, so a body's facts are found without running it.

## Portability and contention

No core type has mutable heap state of its own, since a value appears to change only through a `var` or an `inout`. So every core value may go to another task, and only one task reaches it at a time ([modes.fixed-values](../13-modes.md#modes.fixed-values), [modes.contended-values](../13-modes.md#modes.contended-values), [modes.mode-crossing](../13-modes.md#modes.mode-crossing)). Two types change that. A view, which reads storage that its own task owns, is fixed. A `Shared<T>`, which several tasks reach, is contended, and it is portable, since sending a handle to another task is what it is for. The thread axes read a type's declaration once. Marker traits, as Rust's `Send` and `Sync`, are rejected: they restate what a type's declaration already says, and every generic signature would carry them.

## Demands

A feature that needs a mode demands it where the use is written ([modes.demands](../13-modes.md#modes.demands)), after type checking, so a demand never changes a type. No core value is fixed or contended, and core holds no view. So no core program can fail a check of modes, and the modes add no error to code that uses none of the advanced tier's features. Every diagnostic that a demand raises has one shape ([modes.diagnostic-shape](../13-modes.md#modes.diagnostic-shape)). One line names the value and the axis, and one note is at the line that gave the value the mode. A demand whose message can't take that shape isn't added, since a mode error the reader can't act on is worse than none.

## Showing modes

`stilt show` prints a mode only where it isn't the default ([modes.show](../13-modes.md#modes.show)). Printing every binding's modes is rejected: a core function would gain five words per binding and say nothing new. A closure literal's own locality isn't printed, since no name would carry it. The facts suite states each expected mode at its line ([modes.facts-suite](../13-modes.md#modes.facts-suite)), derived by reasoning from the rules. So the compiler's inference is checked against the rules, and never against itself.

## Views

Core has no way to look into part of a string or a list without copying it: `slice` returns a new value, and each list method returns a new list. Rust answers this with references and lifetimes, and a lifetime is a proof by annotation. A view is a window into part of a value that someone else owns, and which value it looks into is inferred. Within a function, it comes from the place the view is made from ([views.making-view](../13-modes.md#views.making-view)). Across a call, it comes from the signature, since a result can only view the arguments its call passes ([views.across-calls](../13-modes.md#views.across-calls)). The law of exclusivity, with the durations it already has, keeps the viewed value from changing while a view lives ([views.reads-that-last](../13-modes.md#views.reads-that-last), [views.change-while-viewed](../13-modes.md#views.change-while-viewed)).

One type, `View<T>`, covers every viewable type ([views.std-view](../13-modes.md#views.std-view)). Two types, a list slice and a string view, are rejected: one type keeps the rule one sentence, and leaves room for views of other types. Naming the viewed parameter in the signature, as `-> View<str> of line`, is rejected, and so is an error where two parameters could be viewed. A result that views every argument it could view needs nothing written and rejects no program, and only makes some reads last longer. Ending a view's read at its last use is rejected, since it would be the one flow-sensitive rule in the language.

A view can't be stored ([views.view-types](../13-modes.md#views.view-types)) and can't outlive its source ([views.escaping](../13-modes.md#views.escaping)), so it needs no lifetime. Its locality is the demand of [modes.demands](../13-modes.md#modes.demands), and a view is fixed, so it never reaches another task ([views.fixed](../13-modes.md#views.fixed)). `View`, `Iter` and their functions live in `std.view`, outside the prelude, and are no methods of `str`, `List` and `Map`. A method added to a prelude type would conflict with any program that implements a trait with that method's name for the type. Functions for one viewed type, such as `view.get` on a `View<List<U>>`, are functions of `std.view` too ([views.functions-of-views](../13-modes.md#views.functions-of-views)). An impl names a type applied to its own parameters, so `impl<T> View<T>` can't hold them.

E0423 is a soundness rule. A view into a list that the body changes would read freed or moved storage. E0404 guards only against a hidden copy, since `for` over a list reads the list itself. A view's read of a source begins where the operand that gives it is evaluated ([views.reads-that-last](../13-modes.md#views.reads-that-last)), so that in `View.of(xs, bump(inout xs), 2)` evaluation stays left to right and the view still never sees a change: the later change is E0423, where reading `xs` only once the other operands are evaluated would contradict [values.left-to-right](../05-values.md#values.left-to-right), and reading it in its turn with no error would leave a window that shows what a copy doesn't.

**How views are implemented.** The reference interpreter keeps a view as a copy of the viewed part and its offsets, and an iterator as a closure over copies. Under the law nothing can change a source while a view lives, so copies can't be told apart from windows, as copy-in, copy-out can't be told from mutation in place. The compiler keeps a view as a pointer and two offsets into the source's storage. The view holds a reference of its own to the storage, one increment, so that no gap in the rules can read freed memory. The Lean model proves that a window and a copy of the viewed part agree under the law.

## Iterators

An iterator is a lazy sequence ([views.making-iterator](../13-modes.md#views.making-iterator), [views.laziness](../13-modes.md#views.laziness)), so a chain of adapters builds no list at each step, as the eager list methods do. Ranges stay out of the value world: `a..b` is the iterable of a `for`, and `view.range` gives an iterator when one is wanted.

An adapter's closure has an empty row ([views.adapters](../13-modes.md#views.adapters)). It runs when a consumer pulls, in whatever function that is. Its effects would then have to live in the iterator's type, as `Iter<T, row>`, and every signature that passes an iterator would carry a row. A closure that must raise runs under the eager list methods, or inside a consumer's callback, whose effects pass through to the caller ([views.consumers](../13-modes.md#views.consumers)). An adapter's closure captures no view, since the iterator keeps the closure and would then view through it. An iterator has no structural traits ([views.iterator-traits](../13-modes.md#views.iterator-traits)): comparing or showing one would run it.

## Projections

Code that owns a list can't hand out one of its parts for writing with views alone. A function also can't hand its caller a place of its own choosing and resume once the caller is done, as Hylo's subscripts and Swift's `_modify` accessors do. Such places include a computed cell of a grid, a map entry kept in step with a cached maximum, and a view of an `inout` parameter. A projection does both: its body yields a place, and a call of it is a place ([projections.declaring-projection](../13-modes.md#projections.declaring-projection), [projections.call-is-place](../13-modes.md#projections.call-is-place)).

A projection is written `-> inout T`. Inferring which functions are projections from a `yield` in the body is rejected. Whether a call is a place changes what type-checks at every caller, so it belongs in the signature, as `inout` on a parameter does. A projection takes one form, which yields a place for every access, and a reader is a plain function returning `T`. Accessor bundles, as Hylo's `let`, `inout` and `set` subscripts, are rejected to keep the rule one sentence.

`yield` is a statement that runs exactly once on every path ([projections.yield](../13-modes.md#projections.yield), [projections.once-on-every-path](../13-modes.md#projections.once-on-every-path)). As an expression, a `yield` in an operand would make the count of paths hard to read, and the check stays syntactic only for statements. A `yield` inside the operand of a `try … catch` is an error because the arms run whether the raise came before or after the `yield`. The number of `yield`s on a path through an arm would then depend on when the raise came.

A projection can't raise ([projections.cannot-raise](../13-modes.md#projections.cannot-raise)), since a call that is a place can't sit in a `try`'s operand. A `try` on an assignment or an `inout` argument would be a new form for one case. A projection that fails can panic, or its caller can check first.

A projection's call that is read copies the yielded place out and resumes at once ([projections.call-is-place](../13-modes.md#projections.call-is-place)). Suspending a projection for a scope, so that a view or a `for` could hold its place, is rejected. The compiler would turn the rest of the scope into the caller's access, and a reader couldn't see where the projection's arguments stop being held. So every projection's access ends in its statement ([projections.when-projection-runs](../13-modes.md#projections.when-projection-runs)).

**How projections are implemented.** The compiler lowers a projection to a function that takes the caller's access as one more argument, as Swift's `_modify` and Hylo's subscripts are. That argument is a callback given a pointer to the yielded place. `g.at(1, 0) = 5` calls `at` with a callback that stores `5`, and nested projections nest their callbacks. The callback lowering handles recursive projections, which inlining couldn't. The reference interpreter runs the body in a frame of its own, and performs the caller's access on the yielded place in that frame. A raise in the access leaves the frame as a callee that raises does.

## Writable views

A view made through `inout` writes its source ([projections.writable-views](../13-modes.md#projections.writable-views), [projections.what-view-writes](../13-modes.md#projections.what-view-writes)), and a `var` binding of one is writable, so `v[i]` through it is a place ([projections.places-through-views](../13-modes.md#projections.places-through-views)). `View.of`, `View.all` and `view` stay read-only. Nothing beyond `inout`, where the caller already writes it, marks a view that writes: which views write, and what, is inferred as what views read is, and shown. Views of strings are read-only, since nothing writes into a `str` by offset.

A separate type for writable views is rejected: whether a view writes is a fact of where it is made and what binds it. Checking writes at the write, so that `var v = View.of(xs, 0, 1)` is accepted until `v[0] = 1`, is rejected too. A `var` binding of a view type would then be writable in some bodies and not others, by a flow of values that the rules keep lexical. So [projections.writable-bindings](../13-modes.md#projections.writable-bindings) reads the binding once.

A view made from a writable binding has the binding as its source, and not what the binding writes. The alternative, reading what the binding writes, would make `let w = tail.view(0, 1)` an error while `tail` lives. A copy-based implementation of `w` would also miss a write through `tail`. With `tail` as the source, that write is E0423, and every implementation agrees.

E0429 is a soundness rule ([projections.reaching-written-source](../13-modes.md#projections.reaching-written-source)). Without it, a write through a view would change a value that another binding holds, against value semantics, as a counterexample in the Lean model shows. Splitting a list into two views returned as a tuple is rejected. A tuple of views can't be stored, and only `split`, which is native, knows that the two parts don't overlap. The closure that `split` takes gives both parts a scope that ends together. A function can hand back a writable view of its `inout` parameter ([projections.results-that-write](../13-modes.md#projections.results-that-write)), because the caller's binding then holds the write for its scope.

**How writable views are implemented.** The compiler keeps a writable view as a pointer and two offsets into storage that `into`, `part` and `split` have made unique. A write through the view is a write to that storage. The reference interpreter keeps a writable view as a window, which holds the place it writes and its offsets. It replaces each `inout` parameter among its places with the caller's argument when it hands the view back. The Lean model proves that a window, and a copy written back when the binding's scope ends, agree under the law.
