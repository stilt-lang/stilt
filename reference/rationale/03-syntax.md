# Rationale: Syntax

Stilt is written by people and by coding agents. Three choices of this chapter follow from that. The forms that save an agent's tokens belong to the one syntax. Every tool shares one grammar. Every program has one canonical layout.

## One syntax

Some forms shorten the code that programs write most often, and so the tokens spent on each task. They are let-else, the expression-level `else`, key paths, field punning, blocks of one statement on one line, and `/// ex:` examples, and they belong to the one syntax ([syntax.one-syntax](../03-syntax.md#syntax.one-syntax)).

The alternative is a second syntax for agents, applied as a profile of the formatter. It is rejected. Two syntaxes would split the code that people and models learn from, and give every tool two inputs to handle. Each of these forms adds a way to write something without removing another, so none of them needs a separate syntax. The cost is that some things have two spellings, such as a `match` and a let-else, or `|o| o.paid` and `.paid`. The formatter picks one spelling only for field punning.

## Notation

The grammar is written once, in EBNF that people read and that tools generate parsers and decoders from ([syntax.grammar](../03-syntax.md#syntax.grammar)). The Reference, the reference interpreter and the compiler share it, so a form that one accepts the others accept too. The reference interpreter's parser is generated by Menhir, which proves that the grammar has no conflicts. So every tool parses every file one way.

The grammar rejects only what no program could mean. A form that is well formed but wrong, such as a limit named twice or a pack in the wrong place, passes the grammar and is rejected after parsing. Its code then names the mistake. Rejecting it in the grammar would report E0100, which says only that the text doesn't parse.

## Programs

`extern` marks the boundary with C in both directions, and the body tells the two apart ([syntax.extern-functions](../03-syntax.md#syntax.extern-functions)). `pub extern fn` with a body is a function that C calls, and `extern fn` without one is a function that C gives. A foreign function ends at its signature, because nothing a clause or a body could say applies to code that C supplies.

## Declarations

Declarations are written in full, so the grammar can tell each part apart by its form alone. A lowercase generic with a type is a value parameter, and one without a type is a row variable ([syntax.lowercase-generics](../03-syntax.md#syntax.lowercase-generics)). An `escaping` parameter's type is always written with `fn`, so the mark sits on a function type wherever it appears ([syntax.escaping-parameters](../03-syntax.md#syntax.escaping-parameters)).

A list of generics holds at least one ([syntax.generic-lists](../03-syntax.md#syntax.generic-lists)), because `<>` says nothing and would be a second spelling of no generics. A type with a single variant writes its leading `|` ([syntax.variants](../03-syntax.md#syntax.variants)). Without it, `type Id = UserId` would read as an alias, as it does in Haskell or Rust, and Stilt has no aliases. The bar shows that the one-variant type is a variant type.

A `where` clause starts on its signature's line, so a newline after a signature still ends it. A `without` clause may start the next line ([syntax.limit-clauses](../03-syntax.md#syntax.limit-clauses)), because after a long signature it often doesn't fit beside it. The word and its limit together can't begin any statement, so the line can continue the one before it.

## Macros

A macro use is read by the macro's own arms once its name is resolved, never by the grammar ([syntax.macros](../03-syntax.md#syntax.macros)). So a macro can't change how a file parses, and every tool parses every file without expanding a macro. The grammar requires only that a use's tokens balance their brackets, as Rust does with the token trees of its macro uses. That is why `TOKEN` excludes brackets.

## Names and paths

A `use` path accepts an uppercase name after its first, though a `use` imports a module, never an item ([syntax.paths](../03-syntax.md#syntax.paths)). Because `use std.sync.Shared` parses, name resolution can say what is wrong with it. The grammar would only report a syntax error at the `S`.

## Types

`>>` is one token, the shift, and the grammar lets it close two lists of type arguments at once ([syntax.closing-angle-brackets](../03-syntax.md#syntax.closing-angle-brackets)). So nested generic types need no space between their brackets, as in `Map<str, List<i64>>`, which C++ required before C++11.

A value argument of a type is a literal or a name, never a computation ([syntax.value-arguments](../03-syntax.md#syntax.value-arguments)), so deciding whether two types are equal never evaluates code. A row attaches to the innermost function type that has none ([syntax.rows](../03-syntax.md#syntax.rows)). That one rule reads `fn() -> fn() / io / e` without parentheses.

## Patterns

Parentheses work alike in types, patterns and expressions ([syntax.patterns](../03-syntax.md#syntax.patterns), [syntax.type-parentheses](../03-syntax.md#syntax.type-parentheses), [syntax.expression-parentheses](../03-syntax.md#syntax.expression-parentheses)): `(x)` is `x`, and `(x,)` is a one-element tuple. One rule serves all three.

An anonymous record type has at least one field ([records.anonymous-types](../07-types.md#records.anonymous-types)), so its pattern names a field or holds `..`. So `{}` is never a pattern, and `catch {}` reads one way, as a `catch` with no arms.

## Statements and blocks

Whether `{` begins a block or an anonymous record literal is decided by the next two tokens: a name and a `:`, or `..` ([syntax.record-literal-braces](../03-syntax.md#syntax.record-literal-braces)). So the parser needs no names and no types to decide it.

Whether `let p = e else x` is a let-else or a fallback depends on whether `p` can fail to match ([syntax.statements](../03-syntax.md#syntax.statements)). Case makes that a property of the pattern's form. Still, the grammar reads both one way, and the checks after parsing tell them apart.

## Expressions

Only a path whose last name is uppercase, or `Self`, can begin a struct literal ([syntax.expression-paths](../03-syntax.md#syntax.expression-paths)), which the rule on case makes a matter of spelling. A quote parses without resolving names ([syntax.quotes](../03-syntax.md#syntax.quotes)). `type` is a keyword, and `pattern` and `field` are words of the grammar right after `quote`, so every tool reads the code a quote writes. A bound test is the whole condition of an `if` ([syntax.bound-tests](../03-syntax.md#syntax.bound-tests)), so its bounds end at a `{` that nothing else could mean.

## Heads

The head of an `if`, a `while` or a `match`, and the iterable of a `for`, end at the first `{` outside brackets ([syntax.heads](../03-syntax.md#syntax.heads)). So a struct literal or a block can't stand unparenthesized in a head, as in Rust. `if x {` never needs lookahead to tell the block from a struct literal.

## Settling ambiguities

The productions are ambiguous on their own, as most expression grammars are. A short, closed list of rules settles every ambiguity ([syntax.ambiguities](../03-syntax.md#syntax.ambiguities)). So a reader and every tool resolve each one the same way, and no rule elsewhere quietly adds another.

`return` takes an operand whenever one can start ([syntax.longest-operands](../03-syntax.md#syntax.longest-operands)), so `return -1` returns `-1` and never means `(return) - 1`. An `if let`'s pattern ends at its `=` and its head at its `{`, so an `else` between them is the fallback ([syntax.if-let-heads](../03-syntax.md#syntax.if-let-heads)), and every `if let` parses one way.

## Doc comments

Doc comments become tokens that the grammar places ([syntax.doc-comment-runs](../03-syntax.md#syntax.doc-comment-runs)). A doc comment that documents no declaration, or one on a line of code, is a syntax error ([syntax.doc-comment-placement](../03-syntax.md#syntax.doc-comment-placement)). A warning is not enough: a doc comment that attaches to nothing, or to the wrong thing, misleads both the reader and the tools that show docs. Its examples and properties are parsed with the file, so an example that isn't an expression is reported where it is written.

## Syntax errors

A file with a syntax error is read a part at a time, cut before each word that begins a declaration ([syntax.parts](../03-syntax.md#syntax.parts)). So a `}` left out costs one diagnostic, and the declarations after it are still read and checked. Each part reports only its first syntax error, the root cause. An error in a file's encoding is the file's only error ([syntax.first-error](../03-syntax.md#syntax.first-error)), because nothing read from such a file can be trusted.

## The canonical format

There is one canonical format, and it is dense: two spaces per level, braces on their construct's line, a block of one statement on one line ([syntax.format](../03-syntax.md#syntax.format)). Dense code costs fewer lines and fewer tokens to read and to write.

The formatter has no options ([syntax.no-options](../03-syntax.md#syntax.no-options)), as `gofmt` has none. A configurable formatter, as rustfmt and Prettier are, is rejected: every option creates another canonical form, which makes diffs noisier and content hashes less stable. The format depends on the syntax tree and the comments only, so the hashes behind path-and-hash edits depend on a single text ([edits.hash](../19-tools.md#edits.hash)). The cost is that nobody chooses a style.

When a construct doesn't fit, its outermost group breaks first ([syntax.format.signatures](../03-syntax.md#syntax.format.signatures)). Breaking the innermost group first is rejected. `-> List<(` splits a type across lines, which reads worse than a parameter per line, and pushes the reader past the signature to find what the function returns.

The branches of an `if` that doesn't fit all go on lines of their own ([syntax.format.if-chains](../03-syntax.md#syntax.format.if-chains)). Keeping the branches that fit on one line is rejected: the branches of one `if` read as one construct, and a mixed layout hides its shape. `gofmt` and `rustfmt` break them all.

A list of literals fills its lines ([syntax.format.literal-lists](../03-syntax.md#syntax.format.literal-lists)). One element per line for every list is rejected. A table of 64 constants, as MD5 has, would take 128 lines, and programs would nest their tables or split their files to keep them readable. A list of lists keeps one row per line, so a table still reads as rows.

## Tree form

`parse --sexp` exists for differential testing of parsers ([syntax.tree-form](../03-syntax.md#syntax.tree-form)). Two implementations agree on a file when they print the same bytes. So the tree drops what doesn't change meaning, such as grouping parentheses and punning ([syntax.tree-form.normalizations](../03-syntax.md#syntax.tree-form.normalizations)), and spells everything else one way.

## Published grammars

Constrained decoders let a model write code that the grammar accepts at every step, so it never emits a syntax error. The two published forms are generated from this chapter ([syntax.published-grammars](../03-syntax.md#syntax.published-grammars)), so they can't drift from it. A form must never reject a prefix of a program, because that would stop a decoder from writing the program at all. Where a rule isn't context-free, the form accepts more than the language does ([syntax.published-grammars.loosening](../03-syntax.md#syntax.published-grammars.loosening)), and the compiler reports what the form let through.
