# The benchmark suite

The benchmark suite of the goals' [workloads](../docs/design/goals.md#workloads), and `stilt-bench`, the harness that measures Stilt's debug builds and release builds on it against the budgets in [`budgets.toml`](budgets.toml): `release-speed` to `memory`, `cheap-checks`, `small-runtime` and `inline-values`. `just bench` runs it.

| Path | Contents |
| --- | --- |
| [`programs/`](programs/) | The suite: each program's `main.lt`, its raising variant `raising.lt`, its wrapping variant `wrapping.lt`, and its Rust baseline `baseline.rs`, which prints the same output |
| [`micro/`](micro/) | Microbenchmarks, each with its raising variant (`free-success`) |
| [`empty/`](empty/) | The empty program in each language, whose peak memory is the runtime's fixed memory (`small-runtime`), and whose executables' sizes, in a debug and a release build and Rust's, the harness prints against no budget |
| [`src/`](src/) | The harness |
| [`compile-time/`](compile-time/) | The compile-time benchmark: `logscan`, a log analyzer heavy in compile-time code, with a procedural macro, reflective derives and value parameters, its baseline written without compile-time code, the log both read and what they print, and the edit script that `stilt-latency compile-time` replays on both |
| [`compare/`](compare/) | The comparisons with other languages, which `stilt-bench compare` times against no budget and `just compare` runs: the Perceus paper's programs in Stilt, Rust, Koka, OCaml, Haskell, Swift and Java, and the suite's programs in Go, Swift and OCaml |

The programs are binary-trees, n-body, spectral-norm, fannkuch-redux, mandelbrot, nsieve and fasta, after the Benchmarks Game's, on one thread; a JSON writer and parser; a map-heavy and a string-heavy program; sorting; matrix multiplication; a bytecode interpreter; a pipeline of closures over records; and the Game of Life.

## Rules

- **Baselines.** Each baseline is idiomatic safe Rust with the same algorithm, the same threading and a library of the same class: the standard library's collections for Stilt's, and no crates. It uses `unsafe`, SIMD intrinsics or arenas only where the Stilt program uses the equivalent feature, so no baseline does. Integers stay within range, since Stilt panics on overflow where Rust's release profile wraps.
- **Raising variants.** A program's `raising.lt` is its `main.lt` with a raising row on every function, `raise<Fail>` for a variant type `Fail` that nothing raises, and `try` before every call of the program's functions. A change to one changes the other.
- **Wrapping variants.** A program's `wrapping.lt` is its `main.lt` with each integer `+`, `-` and `*`, and each assignment of one, written wrapping, `+%`, `-%` and `*%` ([numbers.wrapping](../reference/06-numbers.md#numbers.wrapping)), so that its release build checks no overflow; a float's operators stay as they are, since a float doesn't wrap. A change to `main.lt` changes it too.
- **Allocators.** Each side allocates as its language does by default: a Stilt program through its runtime's cache of freed small blocks, one list for each size, which serves most allocations without the system's allocator, and a Rust baseline through the system's allocator, by `Box` and `Vec`. Programs that allocate many small objects, binary-trees above all, measure the allocators as much as the code; a Rust program that wanted the same would link an allocator of that kind, such as mimalloc, which a baseline built without crates can't, so `release-speed` measures each program that has such a twin in [`compare/alloc/`](compare/alloc/), binary-trees among them, against its baseline linked with mimalloc, the Rust a programmer would write for it, and `just compare` measures the Perceus paper's programs that way too ([`compare/README.md`](compare/README.md), Against Rust with mimalloc).
- **Sizes.** Each program takes its size as its first argument, the same in its four versions: a tree's depth, a permutation's length, a grid's side or a count of iterations. Without one it runs at the size it writes as its default, for tens to hundreds of milliseconds, long enough for its runs' cycles to be stable and short enough for `just bench` to run in CI in about a minute. `just bench --long` gives each program its size of [`long.toml`](long.toml), at which its Rust baseline runs for at least a second, so that process start, page faults and the timer's resolution are a small part of each time, as published results are measured. `just bench` judges the budgets at the default sizes, which CI runs, and `--long` prints the same verdicts at its own.

## Measurement

The harness builds each Stilt program with `stilt build`, the debug build that `clean-debug-build` times, and with `stilt build --release`, its release build ([builds.release-builds](../reference/20-builds.md#builds.release-builds)), and each baseline with `rustc -C opt-level=3`, Rust's release profile. It builds the release build from an empty cache, timing it, the wrapping variant's release build, and a release build with a profile: a copy of the program whose debug run `stilt run --profile` counted, which writes its profile beside it ([builds.profiles](../reference/20-builds.md#builds.profiles)). It checks that a program, its raising variant, its release build, its wrapping variant's, its release build with a profile and its baseline print the same output, runs each once untimed, since a system may check a new executable on its first run, then counts `--runs` timed runs, the six taking turns, and takes as each one's time that of its runs' counts added together, divided by their number: its cycles on the performance cores at the reference machine's clock ([Goals](../docs/design/goals.md#how-to-read-the-goals), Timing). Each program's row ends with its spread, the largest among its six versions of the slowest run's time less the fastest's, over their mean, so a ratio is read beside how far its runs differ. `release-speed` is the geometric mean over the suite of each release build's time divided by its baseline's, or its baseline's linked with mimalloc where `compare/alloc/` has that twin (Allocators, above), measured without profiles, since the baselines use none, and printed with them too, against no budget; it must also hold with any one program left out, so that no single program carries it, and the report gives the largest of those means. `no-outliers` is the largest such ratio; `memory` is the geometric mean of each release build's peak resident memory, the least of its runs, divided by its baseline's; `cheap-checks` is the geometric mean over the suite of each release build's time divided by its wrapping variant's, and the largest cost of one program's checks, the lesser of that ratio and the ratio of the instructions they retire: time exceeds what the checks cost only when something else moves it, as the allocator moves binary-trees' runs by up to 70% at the default sizes, and instructions exceed it only where the processor overlaps them, as it does spectral_norm's, while a real slowdown raises both; binary-trees' is the largest, since its checked sum must add in the order it is written, where wrapping additions let LLVM turn its recursion into a loop; each release build's time to build is printed, against no budget (Goals, Compile speed); `debug-speed` is the geometric mean over the suite of each debug build's time divided by its baseline's; `free-success` is the geometric mean of each raising variant's time divided by its program's, and the largest such ratio among the microbenchmarks; `small-runtime` is how far the empty program's peak resident memory, the least of its runs, exceeds the empty Rust program's; `inline-values` is the number of boxes that the debug builds of the programs make in all, the heap objects that hold the words of a record, a tuple or a variant of a type that isn't recursive, which the runtime counts and reports at the end of a run when `STILT_COUNTS` is set, from a run of its own. `--filter` runs part of the suite and checks no budget.
